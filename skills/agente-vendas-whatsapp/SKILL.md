## 🗺️ Repository and System Architecture (current)

The repository (this same folder, `C:\Users\fmtol\agente-ia-vendas\agente-ia-vendas\`) is the **engine** — shared code that runs for every client:
- `templates/shared/agent_core_template.py` → core AI logic (call model, handoff/purchase-intent detection, frustration/repetition detection)
- `templates/shared/sessions_template.py` → SQLite schema, lead tracking, metadata
- `templates/whatsapp/agent_template.py` → message handling, BANT flow orchestration, media tags
- `templates/whatsapp/watcher_template.py` → Evolution API polling loop, TTS, follow-ups, watchdogs

**Multi-client production:** one VPS can run several clients — shared code in `/opt/agente/`, per-client data in `/opt/clientes/<cliente>/` (see section 20 for the full architecture). **Client-specific facts (VPS IP, instance name, owner_phone, WhatsApp number) live in the sibling folder `../agentes-ia-vendas-<cliente>/`, not in this repo.**

## 🛠️ Operational Workflows

### 1. Updating the System Prompt or Pricing
The canonical source of the prompt is the `SYSTEM_PROMPT = """..."""` block in `templates/shared/agent_core_template.py`. `config.json`'s `"system_prompt"` is a *copy* consumed by the generator — keep them in sync or the next regeneration silently reverts your edit.
1. Edit `SYSTEM_PROMPT` in `templates/shared/agent_core_template.py`.
2. Sync it into `~/.meu-agente/config.json` (regex-extract the triple-quoted block and write it to `cfg["system_prompt"]`).
3. Run `python setup/generate_meu_agente.py` to rebuild the Windows staging copy.
4. **Deploy to the VPS (section 8)** — steps 1–3 alone do NOT touch production.
5. Restart the systemd service (section 6).

### 2. BANT Prompt Constraints & Rules
**Movido pro arquivo do cliente** — regras de negócio (o que a IA pode/não pode recomendar, competidor a nunca mencionar, política de preço, manual de medição) são específicas de cada instalação. Ver `../agentes-ia-vendas-agil-persianas/agil-persianas.md`, seção "Regras de negócio (BANT / prompt de vendas)" e "Preço". Regra genérica que vale pra qualquer cliente: **uma pergunta por mensagem** (cadência), e sempre verificar contra o catálogo real do cliente antes de adicionar conselho de produto ao prompt.

### 3. Database & SQL Integrity
- The `leads` table uses exactly **11 bindings** in the `create_lead` SQL insert query inside `sessions.py`. Ensure `now` is supplied for both `created_at` and `updated_at`.
- Use the `session_metadata` table to persist: `width`, `height`, `cep`, `endereco`, `checkout_id`, `asaas_checkout_url`, `checkout_sent_at`, and `followup_status` ("0", "1", "2", "PAID").
- **`endereco` (added 2026-07-31):** full delivery address (street, number, complement, neighborhood), captured by the heuristic `extract_address()` in `agent.py`/`agent_template.py` — looks for a street-type keyword (rua/av/avenida/alameda/...) combined with either a number or the word "bairro". Deliberately not parsed into structured fields (street/number/etc. separately) — Brazilian addresses in free chat text are too irregular to regex reliably, and the raw string is good enough for the merchant to read and for the Asaas payment description. The prompt asks for it as its own step (6.5, right before generating the checkout link) so casual quote-only leads are never asked for it.
- **Fake-link placeholder bug (found & fixed 2026-07-31):** the LLM sometimes decides on its own (per the prompt's step 7 "offer the payment link") that it's time to close, and writes closing text with a literal bracket placeholder like `[Link de pagamento será gerado e enviado aqui]` — **even when the customer's message didn't match any `is_purchase_intent()` keyword**, so the backend never actually generated an Asaas link. The customer would receive a broken, non-functional "link". Reproduced live: user said "não mande o link" after confirming their address, and got the raw placeholder back. Fixed in `agent.py`/`agent_template.py`: `handle_message()` now also checks the AI's own response text for a `LINK_PLACEHOLDER_PATTERN` (`\[...link...\]`, case-insensitive) as a second trigger alongside `is_purchase_intent()`, and if the placeholder is present, substitutes it in-place with the real generated URL instead of appending `format_checkout_message()` (which would have duplicated the closing message). The purchase-intent block was also moved to run **before** the response is saved to `messages`/SQLite (previously ran after) — otherwise the persisted conversation history would contain the fake placeholder text instead of the real link that was actually sent.

### 4. Audio Transcription and TTS Replies
- **Whisper Transcription:** Audio messages are fetched in Base64 via `POST /chat/getBase64FromMediaMessage/{instance}` and transcribed with Whisper (Groq's `whisper-large-v3` preferred, `OPENAI_API_KEY`/`whisper-1` as second choice). You MUST include `"User-Agent": "Mozilla/5.0 ..."` in headers of urllib requests to Groq (`api.groq.com`) to bypass Cloudflare Error 403.
  - **Key lookup order (fixed 2026-07-28):** `~/.config/watch/.env` first, then `groq_api_key`/`openai_api_key` in `~/.meu-agente/config.json`. The `.env` belongs to an unrelated tool and **does not exist on the VPS**, so for months on the server every customer voice note silently produced "Desculpe, não consegui compreender o seu áudio" — the config.json fallback is what makes transcription work in production. When deploying to a new host, put the Groq key in `config.json`, not in the stray `.env`.
  - **ElevenLabs is NOT a substitute** — it only does text→speech. Transcription (speech→text) requires Groq or OpenAI Whisper. Clients conflate the two; state the difference plainly.
  - **Fixed bug (2026-07-25):** the last-resort fallback used to reuse `config.json`'s `ai_api_key` as if it were always an OpenAI key whenever it was >30 chars — but that key is whatever `AI_PROVIDER` is currently set to (Anthropic/Gemini/OpenAI). Since the client runs Anthropic, this silently sent an `sk-ant-...` key as a Bearer token to `api.openai.com`, which 401s every time (audio replies would then just fail with "não consegui compreender seu áudio"). Now gated on `config_data.get("ai_provider") == "openai"` before reusing that key — in `watcher.py` and `templates/whatsapp/watcher_template.py`.
- **Voice Response Synthesis:** Despite this file's older text and the `send_whatsapp_audio` docstring history mentioning `gTTS`, the **live code as of 2026-07-25 uses ElevenLabs exclusively** (`send_whatsapp_audio()` → `send_whatsapp_audio_elevenlabs()`, no gTTS fallback path exists anymore). Reads `elevenlabs_api_key`/`elevenlabs_voice_id` from `config.json` (default voice `21m00Tcm4TlvDq8ikWAM` "Rachel"), preprocesses text via `preprocess_text_for_tts()` (spells out `R$`/decimal values by extenso in Portuguese, adds `...` pauses after punctuation) before calling `POST /v1/text-to-speech/{voice_id}`, then sends the MP3 as base64 via `POST /message/sendMedia/{instance}` with `"mediatype": "audio"`. If `elevenlabs_api_key` is missing, it returns `False` and the caller falls back to a plain text WhatsApp reply — there's no automatic TTS provider fallback anymore.

### 5. Automatic Payment Reminders (Cobrança Ativa)
- The background task `process_payment_followups()` runs periodically in `watcher.py` (every 200 iterations / 10 minutes, including once immediately on startup since `iteration_counter` starts at 0).
- It checks Asaas payment status using `GET /v3/payments?paymentLink={checkout_id}`.
- If unpaid, it sends a 2-hour friendly distraction reminder and a 24-hour scarcity/urgency reminder. If paid, it updates `followup_status` to `"PAID"` and sends a beautiful confirmation.
- Leads currently flagged `human_handoff == "1"` are skipped entirely (see section 9) — no automated nagging while a human is handling the conversation.
- **Fixed bug (2026-07-27):** `followup_status` used to be written **before** `send_whatsapp()`, so a transient Evolution API failure (timeout / HTTP 400) marked the reminder as sent when it never left — that lead then never got a 2h reminder *and* never advanced to the 24h one. Observed live in the log on 2026-07-27 08:39 for lead Fernando. Now `sessions.save_metadata(...)` only runs inside `if send_whatsapp(...):`, so a failure simply retries on the next 10-minute cycle. Keep this shape when editing.
- **Known quirk (not yet fixed, low severity):** the 2h/24h checks are `if elapsed >= 7200 and status == "0"` then `elif elapsed >= 86400 and status == "1"`. If the watcher is down/restarted across the entire 2h–24h window (so the 2h reminder never fired), the next run sees `elapsed >= 86400` but `status` still `"0"`, takes the **first** branch, and sends the "2 hour, need help?" wording ~24h+ late instead of the urgency one — it self-corrects and sends the correct 24h message ~10 minutes later on the following run. Cosmetic (wrong tone once), not a functional loss — mention if a client asks why a lead got two reminder messages close together.

### 6. Restarting the Watcher Service (VPS / systemd)
Whenever production code (`agent.py`, `watcher.py`, etc.) is updated on the VPS, restart the service:
```
systemctl restart meu-agente-watcher
systemctl is-active meu-agente-watcher
tail -n 20 /root/meu-agente/watcher.log
```
Systemd guarantees a single instance, so the old Windows concern about duplicate pollers double-replying no longer applies — but never *also* launch `python3 watcher.py` by hand alongside the service, which recreates exactly that problem.

**⚠️ Restarting can silently swallow an unanswered lead message.** `watch()` loads `watcher_state.json` once at start, then on its very first poll iteration marks every message currently in the last-20-messages window as "seen" **without replying** (anti-flood-on-boot logic) before switching to normal mode. If a customer's message arrives in the window between "last processed" and "watcher back up", it gets marked seen and never answered — and you won't see an error, just silence. Editing `seen_ids` in `watcher_state.json` on disk does **not** fix an already-running process (state is loaded once into memory, and any `save_state()` call overwrites your edit with the in-memory copy). If you suspect a message got swallowed, check `POST /chat/findMessages/{instance}` on the Evolution API directly for the timestamp, and just ask the user to resend — don't restart again to "retry", it repeats the same swallow.

### 7. Windows-Specific Gotchas (encoding, config drift, provider bugs)
- **UTF-8 console/log encoding:** Every `setup/*.py` script and `watcher.py` must reconfigure stdout/stderr to UTF-8 on Windows (`if sys.platform == "win32": sys.stdout.reconfigure(encoding="utf-8"); sys.stderr.reconfigure(encoding="utf-8")`, placed right after the imports) and `logging.FileHandler(...)` must be given `encoding="utf-8"` explicitly. Without this, any print/log containing emoji (✅, 🔍, etc.) crashes with `UnicodeEncodeError` on the default `cp1252` codepage. This fix now lives in all `setup/*.py` files and in both `watcher.py` and `templates/whatsapp/watcher_template.py` — keep it when regenerating.
- **`connect_whatsapp.py` QR display:** Evolution API's `/instance/connect/{instance}` response has two QR fields: `code` (raw pairing string — feed this to the `qrcode` library for ASCII terminal rendering) and `base64` (a ready-made PNG data URL — only useful for `show_qr_image`/opening as a file). The old code tried to `base64.b64decode(...).decode("utf-8")` the PNG bytes as if they were the raw pairing text, which always throws `UnicodeDecodeError` (PNG magic byte `0x89` isn't valid UTF-8). Fixed: `show_qr_terminal` now takes the raw `code` string directly; `display_qr(qr_code_raw, qr_base64)` picks whichever is available. If a user says the ASCII QR "doesn't scan" in their terminal, fall back to `show_qr_image(qr_base64)` directly (opens as a Windows image file, much easier to scan than tiny terminal glyphs).
- **Config drift between `config.json` and the generated agent:** `AI_PROVIDER` / `AI_MODEL` / `AI_API_KEY` are baked as hardcoded constants at the top of `meu-agente/agent_core.py` (and mirrored in `meu-agente/.env`, though `.env` is NOT read at runtime by `agent_core.py`). Updating `~/.meu-agente/config.json` alone (e.g. via `config_manager.save()`) does **nothing** to the live agent — you must edit `agent_core.py`'s `AI_PROVIDER`/`AI_MODEL`/`AI_API_KEY` constants directly (or regenerate from `agent_core_template.py`), update `.env` for consistency, and then restart the watcher (section 6). Always verify by grepping `agent_core.py` for these constants before assuming a provider/key swap took effect — this exact drift once left an agent running on a stale Gemini key for a day after the user had switched to Anthropic in the setup conversation.
- **Anthropic 400 Bad Request from `[SISTEMA: ...]` price/shipping injections:** `agent.py`'s `handle_message()` injects dynamic pricing/shipping instructions as `{"role": "system", "content": ...}` **inside** the `messages` list (see step 4 in section 1, `prompt_injection`). OpenAI and Gemini's OpenAI-compatible endpoint both accept a `system`-role message anywhere in the array, but **Anthropic's `/v1/messages` only accepts `user`/`assistant` roles in `messages`** — a `system` entry there causes an HTTP 400. Because `call_anthropic()` used to swallow `HTTPError` into `f"Erro Anthropic: {e.reason}"` and return it as the chat reply, this bug shipped the literal string **"Erro Anthropic: Bad Request" straight to the customer on WhatsApp** whenever a lead had already given measurements (which is exactly when the price injection fires). Fixed in `agent_core.py`/`agent_core_template.py`: `call_anthropic()` now strips any `role: "system"` entries out of `messages` and folds their content into the top-level `system` parameter instead, and on any remaining API error it logs `e.code`/`e.reason`/the response body via `print()` and returns a graceful Portuguese fallback ("Desculpe, tive um probleminha técnico...") instead of leaking the raw error to the lead. When debugging "the agent sent a weird/technical message to a customer," always suspect this pattern first — reproduce with `handle_message(phone, name, text)` directly against the customer's real phone number (their saved session/metadata is often what triggers provider-specific edge cases that a fresh test number won't hit).
- **Verified working model string:** `claude-opus-4-6` (tested live against the real Anthropic API on 2026-07-25) — use this unless the user asks for a different Claude model.

### 9. Human Handoff (added 2026-07-28)
When a lead asks for a human, the agent steps aside instead of talking over the operator.
- **Detection:** `is_handoff_request(text)` in `agent_core_template.py` — keyword list ("falar com atendente", "quero um vendedor", "isso é um robô", etc.).
- **Behavior:** `check_human_handoff()` in `watcher_template.py` runs **before** `handle_message()` in the poll loop. On a new request it sets metadata `human_handoff="1"` (+ `human_handoff_at`), replies to the lead ("já vou te conectar com um de nossos atendentes"), and notifies `OWNER_PHONE`. While flagged, every further message from that lead is logged and skipped — the AI stays silent, and payment follow-ups skip them too.
- **⚠️ No automatic timeout — this is deliberate.** A 24h auto-resume existed briefly and the client explicitly asked for it to be removed on 2026-07-28 ("retirar esse recurso de espera por enquanto"). A flagged lead stays paused until someone clears it manually. Do not reintroduce a timeout without a fresh explicit request.
- **Clearing the flag manually** (on the VPS, from `/root/meu-agente`):
  ```
  python3 -c "import sessions; sessions.save_metadata('whatsapp_<PHONE>', 'human_handoff', '0')"
  ```
  Lead IDs follow the pattern `whatsapp_<phone>`. Expect confusion reports like "the bot stopped answering me" that are actually this feature working — check `human_handoff` before debugging anything else.
- `OWNER_PHONE` comes from `config.json`'s `owner_phone`. **Updated 2026-08-10** (was `555596611311`, the client's own test/lead number — handoff alerts and customer test replies were landing in the same chat, confusing during testing) to `555399709661` (DDD 53, 8 dígitos locais — um a menos que o padrão de celular BR de 9, mas confirmado funcionando: `send_whatsapp()` retornou sucesso e o cliente confirmou o recebimento de um teste real). Update via SFTP direto no `config.json` (não precisa redeploy de código, só restart do serviço pra recarregar o config).

### 10. ⚠️ The "Zombie Connection" — #1 cause of "the agent stopped replying"
**`GET /instance/connectionState` LIES.** It reports the state persisted in Postgres, not the health of the live Baileys websocket. The socket can die while the endpoint keeps answering `{"state":"open"}` indefinitely. On 2026-07-28 the agent was mute for **8 hours** in exactly this state — systemd `active`, process burning normal CPU (polling fine), connectionState `open`, and **zero errors in `watcher.log`**, because from the watcher's point of view it was simply receiving no new messages.

**How to confirm the zombie state (do this FIRST when "it stopped replying"):**
1. `tail /root/meu-agente/watcher.log` → last entry hours old, no errors. (Silence is the symptom; the log only writes on message activity.)
2. `docker logs evolution-api-9ic2-api-1 --since 30m` → completely empty.
3. `fetchInstances` → `updatedAt` frozen hours in the past while `connectionStatus` still says `open`.
4. Run `watcher.fetch_messages()` on the box — if the newest message returned is hours old and predates messages the user swears they sent, Evolution never received them.

**Fix:** `POST /instance/restart/{instance}` (note: **POST**, not PUT — PUT returns 404). It reconnects from stored credentials, **no QR scan needed**, and recovery is immediate (`CONNECTED TO WHATSAPP` in the container log).

**Automated since 2026-07-28:** `watch()` now runs a watchdog every `HEALTH_CHECK_EVERY` iterations (~5 min) — `is_evolution_socket_alive()` probes `POST /chat/fetchProfile/{instance}`, which forces a genuine WhatsApp round-trip (~1.9s, returns freshly-signed profile-pic URLs). After `HEALTH_FAIL_THRESHOLD` consecutive failures it auto-restarts the instance, notifies `OWNER_PHONE` on both success and failure, and respects `HEALTH_RESTART_COOLDOWN` to avoid restart loops.
- **Do NOT use `/chat/whatsappNumbers` as the probe** — it answers in ~0.03s from the local Contact cache and returns `200 OK` even with a dead socket.
- The auto-restart path (probe failing → restart firing) has **not been observed against a real zombie state yet**, only its components tested individually. If a future incident shows the probe returning healthy while messages don't arrive, the probe endpoint is the thing to re-examine.

### 11. WhatsApp Connection & LID Addressing
- **Reconnecting after a drop:** `GET /instance/connect/agente-agil` returns `{code, base64}`. Decode the `base64` data-URL to a PNG and send it to the user to scan. **The QR expires in roughly 20–30 seconds** — have the user sit on WhatsApp → Aparelhos Conectados → Conectar Aparelho *first*, then generate and send. Multiple attempts failed purely from generate-then-chat latency.
- **⚠️ Tell the user not to touch the Evolution manager UI during reconnect.** On 2026-07-28 a reconnect succeeded ("CONNECTED TO WHATSAPP") and then died 11 seconds later; container logs showed `Restarting instance: agente-agil` from `InstanceController` followed by `redis.delete` + `LOGOUT` — the user had clicked Restart/Disconnect in the web dashboard mid-flow. Check `docker logs evolution-api-9ic2-api-1` for `InstanceController` restarts before assuming the code is at fault.
- **Verify with** `GET /instance/connectionState/agente-agil` → `state` must be `"open"`. A `device_removed` / 401 `conflict` in the logs means the phone dropped the linked device and a fresh QR scan is required.
- **LID addressing (fixed 2026-07-28):** WhatsApp now delivers messages from non-contacts with `remoteJid` like `273662850638050@lid` and the real number only in `key.remoteJidAlt`. The old code gated on `key.get("addressingMode") == "lid"`, but that field is often absent even when the JID *is* `@lid`, so it fell through and used the raw LID as a phone number — every reply then failed with `HTTP 400` in a tight loop while the lead saw silence. `extract_message_data()` now prefers `remoteJidAlt` whenever present and **returns `{}` (ignores the message) if the JID is `@lid` with no alt**, since there is no usable number. Note this is a real limitation: such a lead genuinely cannot be answered — it's a WhatsApp privacy behavior, not something the code can work around.

### 13. ⚠️ Anti-Ban: Rate Limits and Number Warm-Up (added 2026-07-29)
**Root cause of the 2026-07-29 incident:** two numbers in a row (`554831999811`, then `5511921202063`) got their outbound sending blocked/restricted after repeated rapid `instance/logout` → `instance/connect` (new QR) cycles plus multiple test messages fired seconds apart to several different contacts. WhatsApp's abuse detection reads this exact pattern — fast reconnects + bursty sends to multiple numbers — as bot/spam activity, regardless of whether the underlying number is a real SIM or a virtual one. The account ended up explicitly restricted in-app ("atividade recente pode caracterizar spam", ~6h ban shown to the user). **Do not repeat this pattern while debugging** — one reconnect, then wait, then at most one test send.

**Rules to follow from now on, always:**
- **Never send more than ~1 message every 30–90s** from automation (random jitter, not a fixed interval). Baileys instances start tripping WhatsApp's anti-spam around 10–20 msgs/minute — the "safe" ceiling used for human-like pacing is far below that.
- **New number warm-up schedule** (must be followed for any newly-connected number, physical or virtual):
  - Days 1–3: use the number **manually** from the phone itself (normal texting) — do not connect it to Evolution/the agent yet.
  - Week 1 after connecting: max ~10–20 automated messages/day, max ~2/minute, max ~6h of activity/day, never 4 days in a row without a rest day.
  - Week 2: ramp to ~30–50/day. Week 3: ~80–100/day. Full trust generally not reached until 25–30 days of clean activity.
- **After ANY reconnect** (QR scan, `instance/restart`, or recovering from a drop), do not send at normal rate immediately — wait several minutes idle, then send at most one message, then resume slowly. Never batch-test multiple recipients back-to-back right after a reconnect.
- **Limit reconnect attempts.** Repeated `logout` + `connect` cycles within a short window (multiple QR generations in minutes) look like account cycling/abuse on their own, independent of message volume.
- **VPS/datacenter IP is itself a minor risk factor** — WhatsApp weighs IP reputation, and datacenter IPs (Hostinger, AWS, etc.) are scored with more suspicion than residential/4G IPs. This isn't fixable here, so keep the pacing extra conservative to compensate.
- **When debugging delivery issues, resist the urge to fire several test messages in a row to isolate the cause.** That exact troubleshooting reflex is what caused the 2026-07-29 incident. Prefer checking `MessageUpdate` status on the *one* message already sent, or asking the human to confirm receipt, over sending another probe.
- **Update 2026-07-29 (later same day):** the ban repeated on a 3rd number (`554891593601`) within hours, on the same day, right after the client reconnected and started using it — same `device_removed`/restriction pattern. This confirms it's the **connection/reconnect behavior itself** that trips WhatsApp's detection, not any specific number. Cycling through more numbers is not a fix and likely makes it worse (each fresh number gets flagged in the same timeframe). When this happens, the right move is to stop touching the connection entirely for the rest of the day (not just 6h) and resume the warm-up schedule above from day 1 on whichever number is used next.

**Implemented in code (2026-07-29):** `process_payment_followups()` in `watcher_template.py` now sends **at most one automated follow-up per call** (`return` right after each successful send), instead of looping through and messaging every eligible lead back-to-back. Since this function only runs every 200 iterations (~10 min, see `watch()`), this alone gives ~10 min of spacing between automated messages to different leads — comfortably above the 30–90s minimum — **without ever blocking the main loop** (no `time.sleep()` was added, since that would freeze real-time replies to whoever messages the bot during the pause). This only affects bulk-style follow-ups; normal 1-on-1 conversation replies (`handle_message()`) are intentionally NOT delayed — replying instantly to an engaged customer is normal human behavior and isn't the pattern that triggers anti-spam.

### 38. Reengajamento de lead que esfria ANTES do checkout (added 2026-08-10)
`process_payment_followups()` (seção 5) só cobre quem **já tem** link de checkout gerado e não pagou — mas na prática a maior parte da desistência num fluxo de várias perguntas (BANT completo, várias etapas) acontece **antes** disso: o lead dá a medida, some, e nunca mais recebia nenhum contato automático. Pedido do cliente depois de eu apontar isso como a melhoria de maior impacto em conversão.
- **`get_leads_sem_checkout()`** (nova, em `sessions_template.py`): retorna todo lead com `sent_checkout = 0` junto com o timestamp da mensagem mais recente (`MAX(messages.ts)`).
- **`process_midfunnel_followups()`** (novo, em `watcher.py`, chamado no mesmo bloco de manutenção periódica de `process_payment_followups()`, ~10 min): mesmo padrão anti-bloqueio (1 envio por ciclo). Só reengaja quem tem `width`+`height` salvos (sinal real de interesse — sem isso, alguém que só mandou "oi" e sumiu não recebe nada, evita parecer spam/perseguição). Dois toques, guardados em `midfunnel_followup_status` (`"0"`→`"1"`→`"2"`, mesmo padrão de `followup_status`):
  - **4h de silêncio:** mensagem citando a medida específica salva (ex: "sua persiana de 1,20m x 1,50m"), tom de "ficou alguma dúvida?".
  - **48h de silêncio:** segunda mensagem, mais leve, sem pressão, "se quiser retomar é só chamar".
- **Reset ao responder:** `handle_message()` zera `midfunnel_followup_status` pra `"0"` toda vez que o lead manda qualquer mensagem nova — sem isso, um lead que respondesse uma vez depois do primeiro toque e sumisse de novo não teria mais nenhum reengajamento na rodada seguinte de silêncio (o status já teria avançado).
- **Validado antes do deploy** com SQLite in-memory simulando 6 cenários (com/sem medida salva, já tem checkout, handoff humano ativo, e os dois estágios de silêncio) — todos bateram com o esperado.
- **Confirmado ao vivo no primeiro ciclo depois do deploy**: disparou pro lead real Fernando (555199980089, 4h de silêncio, medida 1,5m x 1,5m salva) — `📤 Enviado para 555199980089` no log e `midfunnel_followup_status` virou `"1"` no banco, exatamente como esperado.

**⚠️ Bug real encontrado minutos depois, em produção (mesmo dia):** o prazo do 2º toque (`elif elapsed >= MIDFUNNEL_SECOND_NUDGE_SECONDS and status == "1"`) usava `elapsed` calculado a partir de `last_ts` (última mensagem do CLIENTE) — mas isso **não muda** enquanto o lead fica em silêncio. Esse mesmo Fernando já estava sem responder há muito mais que 48h quando o 1º toque saiu; no ciclo seguinte (disparado por um restart do serviço minutos depois, não 48h depois), `elapsed` desde `last_ts` já satisfazia os dois `if`/`elif` ao mesmo tempo, e o 2º toque saiu **4 minutos** depois do 1º. Corrigido salvando `midfunnel_followup_at` (timestamp de quando o 1º toque foi enviado) e usando **esse** valor como base do prazo do 2º toque, nunca `last_ts` de novo. `tests/test_midfunnel_followups.py` reproduz esse cenário exato (lead "sumido" há 5 dias, dois ciclos rodados minutos um do outro) — só peguei o bug depois que ele já tinha acontecido de verdade; o teste original só cobria os estágios isoladamente, não a sequência 1→2 rodada logo em seguida. **Lição:** ao testar lógica de "N toques com prazos progressivos", sempre simular os ciclos EM SEQUÊNCIA (não só cada estágio isolado) e incluir um cenário onde o "silêncio original" já é muito maior que todos os prazos — é exatamente esse caso que expõe confusão entre "tempo desde eventro X" vs "tempo desde o toque anterior".

### 39. Detecção de cliente travado/frustrado — handoff sem pedido explícito (added 2026-08-10)
Até aqui `check_human_handoff()` só escalava pra atendente em pedido explícito (`is_handoff_request`). Um cliente repetindo a mesma dúvida, ou hesitando várias vezes sem sair do lugar, não era pego por nada — virava venda perdida silenciosa, sem ninguém saber que aquele lead precisava de ajuda humana. Pedido do cliente depois de eu apontar isso como o maior ponto cego do agente.
- **Dois sinais independentes** (`agent_core_template.py`), cada um soma no mesmo contador:
  - **`is_frustration_keyword(texto)`:** lista de ~25 frases/padrões em português ("não entendi", "já falei isso", "isso não resolve", "cansei disso", etc.), mais `"??"` (dupla interrogação) e mensagem toda em MAIÚSCULAS com 15+ letras (evita falso positivo em sigla curta tipo "CEP" ou "OK").
  - **`is_repeated_question(texto, mensagens_anteriores)`:** compara a mensagem atual (via `difflib.SequenceMatcher`, ratio ≥ 0.6) com as últimas mensagens do próprio cliente. **Pega hesitação repetida de graça** — "não sei" dito duas vezes é, por definição, muito similar a si mesmo, não precisou de lista própria pra isso. Ignora mensagens com menos de 8 caracteres pra não disparar em "oi"/"sim"/"ok", que são naturalmente parecidas entre si sem indicar nada de errado.
- **`FRUSTRATION_THRESHOLD = 2`:** um sinal isolado NÃO escala sozinho (pode ser brincadeira/coincidência) — só pausa a IA ao acumular 2 sinais. `frustration_signal_count` em `session_metadata`, mesmo padrão de `followup_status`/`midfunnel_followup_status`.
- **Reset automático em progresso real:** `handle_message()` zera o contador toda vez que extrai `width`/`height`/`cep`/`cor`/`endereco` novos da mensagem — um sinal de confusão lá no início da conversa, já contornado com sucesso, não deve continuar pesando pra sempre até um sinal novo e sem relação bem mais tarde.
- **Mensagem ao cliente é diferente do handoff explícito** — proativa/cuidadosa, não "você pediu e eu obedeci": *"Percebi que talvez eu não tenha esclarecido direito sua dúvida — vou chamar um de nossos consultores pra te ajudar com mais atenção..."*. Notificação pro `OWNER_PHONE` inclui o motivo (repetição e/ou linguagem de frustração) e as últimas 3 mensagens do cliente, pra o humano entender o contexto rapidinho sem precisar ler o histórico inteiro.
- **Implementado nos dois transportes** (`watcher.py`/Evolution, o de produção, e `webhook_server.py`/Meta Cloud API, mantido em sincronia mesmo não estando ativo) — a mesma lógica central (`is_frustration_keyword`/`is_repeated_question`) vive em `agent_core_template.py`, compartilhada.
- **`tests/test_frustration_detection.py`** (22 casos): cobre os dois detectores separadamente (positivos e negativos, incluindo os guardas contra falso positivo — sigla maiúscula curta, resposta curta genérica, pergunta normal com uma interrogação só) e a lógica de contador/threshold/reset. Rodar antes de qualquer mudança nessa área.

### 41. Módulo de Agendamento (added 2026-08-11)
Mesmo motivo da seção 40 — parte do combo "vendas + atendimento" que um cliente novo pediu no mesmo agente. Diferente de pós-venda, agendamento **não confirma sozinho**: fica pendente até um humano confirmar, porque não existe integração com agenda/calendário real ainda (decisão deliberada — evita prometer um horário que na prática pode não existir).
- **Tabela `appointments`** (`sessions_template.py`): `lead_id`, `phone`, `tipo` (inferido do texto: "instalação"/"visita técnica"/"demonstração"/"atendimento"), `data_hora_texto` (texto livre — mesmo raciocínio de `endereco`, seção 3: data/hora em chat natural é irregular demais pra estruturar sem um parser de datas dedicado, então guarda a frase bruta e deixa o humano confirmar), `status` (`pendente`/`confirmado`/`cancelado`).
- **Detecção em duas camadas:** `is_scheduling_request(texto)` (palavras-chave: "agendar", "marcar visita", "disponibilidade"...) **E** `_has_datetime_hint(texto)` (dia da semana, "amanhã", hora tipo "14h"/"9:30", data tipo "20/08") — as duas juntas, pra não abrir um pedido de agendamento só porque o lead perguntou "vocês agendam visita?" sem dar nenhuma data real ainda.
- **Fluxo:** ao detectar os dois sinais, `handle_message()` cria o agendamento como `pendente` (se já não existir um pendente pro mesmo lead — evita duplicar), injeta instrução pra IA confirmar o pedido SEM prometer confirmação definitiva ("vou confirmar com o responsável"), e devolve uma notificação pro dono.
- **⚠️ Mudança de contrato: `handle_message()` agora retorna uma tupla de 4** (`resposta, media_requests, forcar_texto, owner_notifications`) em vez de 3 — mesmo padrão de mudança já feito uma vez (seção 37, de 2 pra 3). Todo call site foi atualizado: `watcher.py`, `webhook_server.py`, e o CLI `--chat` de `agent.py`. `owner_notifications` é uma lista de strings que quem chamar deve mandar pro `OWNER_PHONE` depois de processar a resposta ao cliente.
- **Confirmação/recusa:** o dono manda `confirmar agendamento 5585999999999` ou `cancelar agendamento 5585999999999` pro número do agente (`handle_owner_command()`) — os dois casos avisam o cliente automaticamente (confirmação inclui a data/hora pedida; recusa pede pro cliente sugerir outro horário).
- **Testado** em `tests/test_order_and_scheduling.py` (`is_scheduling_request`, `_has_datetime_hint`, `_infer_appointment_tipo`) e validado com smoke test manual do SQL.

### 42. Módulo FAQ / Base de Conhecimento (added 2026-08-11)
Mais simples que pós-venda/agendamento — não precisa de detector de intenção nem de tabela nova, porque a própria IA já reconhece uma dúvida frequente pelo contexto se ela estiver disponível no prompt.
- **Arquivo por cliente:** `/opt/clientes/<cliente>/faq.json` — lista de `{"pergunta": "...", "resposta": "..."}`. Se o arquivo não existir (cliente sem FAQ cadastrado), o mecanismo simplesmente não injeta nada — zero impacto pra quem não usa.
- **Mecanismo:** `agent_core_template.py` lê o arquivo em tempo de execução (na importação do módulo) e acrescenta um bloco formatado (`P: ... / R: ...`) direto no `SYSTEM_PROMPT`, com a instrução de **nunca inventar** política/prazo/garantia que não esteja na lista. Pra atualizar uma resposta, basta editar o `faq.json` e reiniciar o serviço — não precisa regenerar o prompt inteiro.
- **Por que não tem detector de código:** ao contrário de pós-venda (que precisa buscar um status real no banco) e agendamento (que precisa abrir um registro pendente), FAQ é só conhecimento — a IA decide sozinha quando uma pergunta bate com uma entrada, igual já faz com preço/regras de negócio no resto do prompt.
- **⚠️ Não vem pronto — precisa ser perguntado no onboarding.** Diferente de pós-venda/agendamento/NPS (que funcionam sem nenhum dado extra), esse módulo fica inerte até existir um `faq.json` real. **Pergunta a acrescentar no onboarding de qualquer cliente novo:** "Quais as dúvidas mais comuns que seus clientes fazem, e como você responde?" — vira as entradas do `faq.json` daquele cliente.

### 43. Módulo Pesquisa de Satisfação — NPS (added 2026-08-11)
- **Tabela `nps_responses`** (`sessions_template.py`): `lead_id`, `phone`, `context` (ex: "pedido #3"), `rating`, `comment`, `status` (`pendente`/`respondido`).
- **Disparo:** quando o dono marca um pedido como entregue (`pedido NUMERO entregue` — comparação por substring `"entreg" in novo_status.lower()`, já que o status é texto livre, não um enum fixo), `handle_owner_command()` cria a pesquisa pendente (`create_nps_request`) e manda a pergunta de nota (0-10) pro cliente, na sequência do aviso de status.
- **Captura da resposta:** `handle_message()` verifica `get_pending_nps(lead_id)` a cada mensagem nova; se existir pendência, `_extract_nps_rating(texto)` tenta achar uma nota **no início** da mensagem (com ou sem a palavra "nota" na frente — "9", "nota 8", "10, adorei" batem; uma mensagem qualquer no meio da conversa não bate, de propósito, pra não confundir nota com número de outra coisa tipo CEP/medida). Achando, salva (`save_nps_response`) e injeta `[SISTEMA: ...]` pra IA agradecer sem tentar vender de novo na mesma mensagem. Não achando, injeta instrução pra responder o assunto normal sem insistir na pesquisa.
- **Limitação conhecida:** o disparo é síncrono, só no momento do comando "entregue" — não existe (ainda) um lembrete automático pra quem recebeu a pergunta e nunca respondeu.

### 47. ⚠️ CORREÇÃO: serviço systemd não era genérico de verdade — quebraria o 2º cliente (added 2026-08-11)
**O bug:** dois lugares diferentes assumiam, na prática, que só existiria UM cliente rodando na VPS, apesar da arquitetura multi-cliente (seção 20) já existir desde 2026-08-02:
1. `setup/deploy_multicliente.py` gravava a unidade systemd em `/etc/systemd/system/agente@.service` com o **nome do cliente escrito dentro do conteúdo do arquivo** (`Environment=AGENTE_CLIENTE={cliente}`, via `.format(cliente=cliente)`), em vez de usar o mecanismo nativo de template do systemd. Instalar um cliente novo **sobrescrevia** esse arquivo — o cliente já instalado continuava rodando (o processo não para sozinho), mas a definição de serviço dele ficava corrompida: um restart futuro dele reiniciaria com o `AGENTE_CLIENTE` do cliente mais recente, não o dele próprio.
2. `deploy/deploy_vps.py` (deploy do código compartilhado via git) reiniciava só um `SERVICE_NAME` fixo (`agente@agil-persianas.service`) — com um segundo cliente instalado, ele ficaria sem reiniciar depois de toda atualização de código compartilhado, silenciosamente desatualizado.

**Nunca chegou a se manifestar em produção** porque só existiu um cliente (Ágil Persianas) até este ponto — encontrado e corrigido de propósito **antes** de instalar o segundo cliente, não depois de um incidente real.

**A correção:**
- As unidades systemd (`UNIT_WATCHER`/`UNIT_WEBHOOK` em `setup/deploy_multicliente.py`) agora usam `%i` — o texto depois do `@` em `systemctl start agente@<cliente>` — em todo lugar que antes tinha `{cliente}`. Isso as torna **genéricas de verdade**: o mesmo arquivo em `/etc/systemd/system/agente@.service` atende qualquer cliente, presente ou futuro, sem nunca precisar ser reescrito. Gravar esse arquivo de novo a cada deploy continua acontecendo, mas agora é inofensivo (idempotente — o conteúdo é sempre o mesmo texto).
- `deploy/deploy_vps.py` ganhou `descobrir_clientes()` (lista as pastas com `config.json` em `/opt/clientes/`) e `reiniciar_servicos()` (plural — reinicia o serviço de **cada** cliente encontrado, não um nome fixo).
- **Mesma correção replicada em `padrao/deploy/deploy_vps_base_template.py`** — a base usada por futuras categorias já nasce com o padrão certo, sem herdar esse bug.
- **Ainda não aplicado na VPS real** — a correção está no repositório (código-fonte dos scripts de deploy); o arquivo de unidade systemd que já está em `/etc/systemd/system/` na VPS ainda é o antigo (baked pra `agil-persianas`, mas funcionando, já que é o único cliente hoje). Ele será substituído automaticamente pelo genérico na próxima vez que `setup/deploy_multicliente.py --deploy` rodar — o que deve acontecer **antes** de instalar o segundo cliente, não depois.

### 20. Arquitetura Multi-Cliente (`client_config`, added 2026-08-02)

### 31. TTS — "nº"/"n°" → "número", "6x" → "seis vezes", "m²" → "metro(s) quadrado(s)" (added 2026-08-03)
Cliente relatou que a voz não conseguia falar "vezes" nem "número" mesmo depois de todos os ajustes acima. Causa raiz real (lida direto no código, não suposição): **nenhuma dessas conversões existia** em `preprocess_text_for_tts()` — "nº" (símbolo de ordinal) nunca virava "número", e "6x" (sem espaço) nunca era pego pelo replace de `" x " → " por "` (que exige espaços). Corrigido com dois `re.sub` novos logo depois do bloco de CEP: `\bn[º°]\s*` → `"número "`; `\b(\d+)x\b(?!\d)` → `"{numero por extenso} vezes"` (o `(?!\d)` evita mexer em medida tipo "10x20").
- **Auditoria adicional (pedido do cliente: "corrija tudo que possa ser similar"):** achado o mesmo tipo de bug em **"m²"** (metro quadrado), usado de verdade no `system_prompt` no preço de Tela Mosquiteira/Toldo (seção 24) e nunca expandido antes do TTS. Corrigido com cuidado de ordem: a conversão de "m²" roda **depois** dos blocos de medida/decimal (senão "1,80 m²" virava "um metro e oitenta centímetros", errado — área não é comprimento) e distingue singular/plural: "o m²" (preço por unidade, ex: "R$180 o m²") → "o metro quadrado" (igual "o quilo"); "1,80 m²" (quantidade) → "metros quadrados".

### 32. TTS — "cartão" vira "cartal"/"cartel" em contexto de parcelamento (CONFIRMADO, added 2026-08-03)
**Bug real, confirmado de ouvido pelo cliente** (não artefato da transcrição Whisper usada pra diagnóstico — testado e ouvido diretamente). A palavra "cartão" sozinha, ou em qualquer posição normal da frase, sai perfeita. Mas especificamente quando a frase fala de parcelamento (ex: "em até 6x/seis vezes sem juros no cartão"), "cartão" sai quebrado — reproduzido de forma quase determinística (~20 de ~22 gerações de teste falharam nesse padrão exato).
- **O que NÃO resolveu** (testado exaustivamente antes de aceitar que é troca de palavra): `stability` 0.55/0.7/0.85, `speed` 1.05/1.0/0.9, `similarity_boost` baixo, reordenar a frase (cartão no início/meio/fim), separar em duas frases distintas, trocar "vezes" por "parcelas", tirar o til ("cartao"), adicionar "de crédito" depois (~50% de falha ainda).
- **O que resolveu:** trocar a palavra **"cartão" por "crédito"** nessa fala — "no crédito"/"no seu crédito" é sinônimo natural e comum em checkout/PDV no Brasil pra "parcelado no cartão de crédito". Testado 9/9 limpo em variações diferentes, e confirmado de ouvido pelo cliente no áudio final. Único uso de "cartão" no `system_prompt` inteiro é essa forma de pagamento (nunca aparece em outro contexto) — troca é segura, feita só na fala (TTS), a mensagem de texto do WhatsApp continua escrevendo "cartão" normalmente. Implementado como os dois últimos `re.sub` de `preprocess_text_for_tts()`: `cartão de crédito` → `crédito`, depois `cartão` (sozinho) → `crédito`.
- **Lição pro futuro:** quando um glitch de pronúncia se repete de forma quase determinística (não varia mudando `stability`/`speed`/frase), pare de tunar parâmetro e teste troca de palavra — é mais rápido e mais confiável que perseguir a causa fonética exata.

### 33. TTS — "16mm"/"25mm"/"50mm" (largura de lâmina, Horizontal Alumínio) (added 2026-08-05)

- **Emoji nos cabeçalhos do prompt (🧵🧠🙅🗺📸📖📐🏠⚠, e seta → usada em tabela de referência):** confirmado que só aparecem em títulos de seção e sintaxe interna de tabela (instrução pra IA, não texto que ela fala pro cliente) — risco baixo, mas **corrigido preventivamente mesmo assim**: `preprocess_text_for_tts()` agora remove qualquer emoji (blocos Unicode `\U0001F300-\U0001FAFF`, `☀-➿`, `←-⇿`, `⬀-⯿` + variation selector/ZWJ) antes de gerar o áudio, mesmo princípio já aplicado ao Markdown — nenhum caso reproduzido ainda, é prevenção pro caso da IA algum dia decorar a resposta com emoji (comportamento comum de LLM). Validado com teste real (frase com 😊/✅ → áudio limpo, sem emoji falado).
- **Acrônimos comuns (PIX, PVC, CEP, Asaas) não testados individualmente** — sem evidência de problema, e são palavras/siglas extremamente comuns em qualquer modelo de voz em português; não mexer sem um caso real reportado (regra geral: só "curar" o que tem evidência real de estar quebrado, não reescrever o que já funciona).

### 35. ⚠️ "Agente não responde em áudio" — NEM SEMPRE é bug de texto, checar a chave ElevenLabs PRIMEIRO (added 2026-08-10)
**Armadilha real:** depois de uma sessão inteira caçando bugs de pronúncia (seções 25-34), veio um relato genérico "o agente não tá respondendo em áudio". O instinto foi procurar mais um bug de texto — mas o `watcher.log` (`tail /opt/clientes/agil-persianas/watcher.log`) mostrava, desde **2026-08-06 21:08** (4 dias antes do relato), `[ERROR] Erro ao gerar/enviar áudio ElevenLabs: HTTP Error 400: Bad Request` em **toda** tentativa, sempre caindo pro fallback de texto (por isso a resposta continuava chegando normal, só sem áudio — fácil de não perceber por dias).
- **Causa raiz:** não era o texto, era a **chave da ElevenLabs em `/opt/clientes/agil-persianas/config.json`**. Reproduzindo a chamada direto (sem passar pelo código) o erro real veio: `{"type":"authentication_error","code":"invalid_api_key","message":"API key ID used as API key - only valid API keys can be used. API keys start with 'sk_'..."}`. A chave salva (64 caracteres, sem prefixo `sk_`) parou de ser aceita — provavelmente a ElevenLabs mudou a validação e passou a exigir só o formato novo (`sk_...`), ou a chave antiga foi revogada/rotacionada do lado deles.
- **Correção:** pedir ao cliente pra pegar a chave secreta atual em elevenlabs.io → Settings → API Keys (sempre começa com `sk_`), atualizar `elevenlabs_api_key` em `config.json` via SFTP, e `systemctl restart agente@agil-persianas.service`. **Nunca tentar adivinhar ou gerar essa chave** — é credencial, só o cliente tem acesso à conta.
- **Lição pro futuro / checklist de diagnóstico pra "não responde em áudio":** antes de sair testando texto/pronúncia de novo, primeiro rodar `tail -80 /opt/clientes/<cliente>/watcher.log` e procurar `[ERROR] Erro ao gerar/enviar áudio`. Se o erro for **HTTP 400 em toda mensagem, sem exceção, independente do conteúdo do texto**, é praticamente sempre autenticação/config (chave errada, revogada, ou saldo/plano ElevenLabs esgotado) — não bug de pronúncia. Bug de pronúncia falha em **frases específicas**, não em 100% das tentativas. Reproduzir a chamada HTTP direto (fora do bot) é o jeito mais rápido de ver a mensagem de erro real, já que o log só grava `str(e)` (`"HTTP Error 400: Bad Request"`, sem o corpo da resposta que tem o motivo verdadeiro).

### 36. Deploy via Git (substitui os patch scripts manuais) + Suite de Testes de TTS (added 2026-08-10)
Depois de uma sessão inteira usando o fluxo manual "baixar arquivo de produção → escrever patch script com match exato de string → SFTP" (frágil, um erro de digitação silenciava a correção inteira), o cliente pediu praticamente que se automatizasse: melhorias de arquitetura pra facilitar reuso/manutenção. Duas mudanças estruturais:
- **`deploy/deploy_vps.py`** (no repositório): clona o repo em `/opt/agente-repo` na VPS (`git clone`, reaproveitando a URL remota com token já configurada localmente) e roda `python3 deploy/deploy_vps.py` de lá. O script renderiza os templates (só `agent_template.py` precisa de replace de import — os outros já usam nomes finais, confirmado byte a byte comparando prod x local em 2026-08-10), confere sintaxe de **todos** os arquivos antes de tocar em produção, faz backup rotativo (só 1, não acumula dezenas de `.bak-*` como antes), aplica e reinicia o serviço. Aborta sem aplicar nada se qualquer arquivo não compilar. Fluxo novo pra qualquer correção futura: editar local → `git commit` + `git push origin main` → na VPS `cd /opt/agente-repo && git pull origin main && python3 deploy/deploy_vps.py`.
- **⚠️ Achado importante nesse processo: a branch `v2` no GitHub é a branch padrão (`origin/HEAD -> origin/v2`) e estava travada muito atrás de `main`** — `main` tinha 40+ commits que `v2` nunca recebeu (praticamente todo o histórico real do projeto), e zero commits exclusivos de `v2` (relação puramente linear, sem divergência — um fast-forward simples resolveria). O clone inicial do `deploy_vps.py` pegou a branch errada por padrão (`git clone` sem `-b` usa o HEAD remoto) até isso ser percebido e corrigido com `git checkout main` no clone da VPS. **Ainda não resolvido:** perguntar ao cliente se quer que `v2` seja atualizada pra bater com `main` (fast-forward, sem risco de conflito) — não fiz isso sem confirmação por ser uma mudança em branch compartilhada/padrão do repositório.
- **`tests/test_tts_preprocessing.py`**: suite de regressão com ~21 casos cobrindo todo bug de TTS já corrigido nesta sessão (nº, 6x, m², cartão→crédito, mm, emoji, markdown, UF, CEP, link, preço, medida). Extrai as funções puras (`number_to_words`, `price_to_words`, `preprocess_text_for_tts`) direto do arquivo fonte via marcador de texto (não importa o módulo inteiro, que depende de `client_config`/`agent` só existentes numa implantação real). **Rodar sempre antes de deploy** que mexer em `preprocess_text_for_tts`: `python tests/test_tts_preprocessing.py`.
- **Bug real que a suite pegou na primeira execução:** `measure_replacer()` pluralizava "metro" errado — condição era `int_part != 1 OR dec_part > 0`, então **qualquer** medida com centímetros virava plural mesmo com exatamente 1 metro (`"1,50 metros"` → texto final `"um metros e cinquenta centímetros"`, concordância quebrada). Cliente relatou isso como "a voz errou centímetros de novo" — a causa real não era a voz nem a palavra "centímetros" isoladamente, era essa quebra gramatical confundindo a prosódia da fala bem naquele ponto (mesmo padrão de outras vezes: texto malformado gera engasgo, não a dificuldade fonética da palavra em si). Corrigido pra `if int_part != 1:` (só pluraliza quando o número de metros inteiros não é exatamente 1), testado com áudio real 3/3 limpo antes de aplicar.
